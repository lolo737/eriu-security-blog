Reboot is not an option

Here's the rule that makes this a real exercise: no rebooting. The user is mid-task, so you have to find the fault live. In real life it's the better habit anyway, because a restart wipes the evidence: the cache, the lease, the route. Nothing left to read, and the fault comes back on Tuesday.

Trace, check, flush, renew

Once the address and gateway look right, these four jobs cover most of what's left. The red line is a hop that stays quiet, and the trace carries on regardless, so that's not a fault.

Same method, other faults


It isn't only networks. Work from the bottom, change one thing at a time, keep the user informed.


New starter can't log in on day one


    

  • The account: enabled, not locked out, not expired, and not set to "must change password at next logon". That last one is normal for a new account and catches people out.
    • 

  • What they typed: the exact error, caps lock, keyboard layout, and the username format (DOMAIN\user or the UPN).
    • 

  • The machine: is it domain-joined and can it reach a domain controller? A first logon can't use cached credentials. Check the clock too, because Kerberos fails when time is out by more than about five minutes.
    • 

  • Timing: a new account may not have replicated to the domain controller this PC is using yet, or synced to the cloud directory.
    • 

  • Don't reset blindly. Verify who they are, then reset with change-at-next-logon.
    • 



A laptop showing 169.254.x.x


    

  • That's the machine giving itself an address because DHCP never answered. DHCP is four steps: Discover, Offer, Request, Acknowledge.
    • 

  • Do other devices on the same network get addresses? If yes, suspect this device: the cable, Wi-Fi or switch port. If nobody does, suspect the DHCP server or scope: out of free leases, service down, wrong VLAN.
    • 

  • On the laptop, release and renew (Windows: ipconfig /release then /renew; Linux: reconnect or nmcli device reapply). Then check the scope on the server.
    •
