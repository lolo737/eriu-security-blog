Incident 014 · Connectivity

Friday morning. I arrive at work at the Four Seasons Hotel beside Berlin Brandenburg Airport, switch on my computer, get logged in and settle in for the day.

Except nothing is loading.

The VPN says it's connected. The network icon looks perfectly happy. Outlook just sits there. Websites time out. I try another browser. Same story.

Right. No internet. Let's not make this more complicated than it needs to be.

First rule: don't start randomly changing settings or rebooting half the building. Find out where the connection stops. Work from the machine outwards, test each hop, and let the evidence tell you what to do next.

A fictional incident, real troubleshooting

The hotel, staff and incident are imaginary. The network layout, commands and diagnostic approach are based on ordinary IT support practice. The addresses and command output below are illustrative documentation values, not live hotel infrastructure.

01Situation — what have we got?

I've got a Windows workstation on the hotel's staff network. It's connected by Ethernet. The VPN client reports that its tunnel is up, but user-facing services aren't responding.

Before touching anything, I check the obvious things. Is the cable seated? Are the link lights on? Is the dock powered? Does the network adapter show as connected? Yes, yes, yes and yes.

That doesn't prove the network is healthy. It proves there's a physical link. Different thing.

Initial observation: physical link and VPN are up. Application access is failing. The fault has not yet been isolated.

02Task — isolate the fault

The job is to restore access without making the problem worse. I want to establish four things:

  • Does the workstation have a valid IP address and default gateway?
  • Can it reach the local gateway and an external IP address?
  • Can DNS translate a hostname into an IP address?
  • Does the VPN route traffic and provide the expected name-resolution settings?

That's the order. If I can't reach the gateway, there's no point blaming DNS. If I can reach an external IP but can't resolve a hostname, that's a much narrower problem.

I'm going to run through the checks from the workstation. Press the button and let the session play. It types the commands, waits for the output and works through the evidence. You can select and copy the terminal text at any point.

I start with the workstation's full network configuration, then test the gateway, an external IP address, DNS and the VPN status. These are the commands I'm using:

ipconfig /all
ping 10.24.18.1
ping 1.1.1.1
nslookup www.microsoft.com
Test-NetConnection 1.1.1.1 -Port 443
Get-VpnConnection

ipconfig /all confirms the workstation has a normal private address, subnet mask, gateway and DNS server. No self-assigned 169.254 address. That's a good start.

The gateway responds. An external IP address responds too, so the machine can reach the local network and get packets out to the internet by IP address.

Then comes the useful bit. The DNS lookup times out. A request for www.microsoft.com gets nowhere. The network connection is working; name resolution isn't.

04Found it — the wrong DNS server

Now we've got something concrete. The workstation is using DNS server 10.24.0.53. It isn't answering queries. The VPN tunnel is up, the gateway is responding and external IP connectivity works. But without DNS, the computer can't turn familiar names into the addresses it needs.

I check the network configuration and the DHCP scope. There it is: the staff-network scope is still handing out the address of an old DNS resolver that has been decommissioned. The setting was never updated after the resolver migration.

That's the fault. Not the cable. Not the switch. Not the VPN service. Not the internet connection. A stale DNS server address being handed to clients.

Don't just change DNS on one laptop and walk away

A manual override might get one person working, but it leaves the underlying DHCP configuration broken. The next device renews its lease and gets the same bad setting. Fix the source of the configuration, then renew the client lease and test again.

05Fix — correct the DHCP scope

I update the staff VLAN's DHCP scope to point to the current internal DNS resolver, 10.24.0.10. I verify the address with the network team and check that the resolver is reachable before pushing the change.

Then I renew the workstation's DHCP lease, flush its local DNS cache and reconnect the VPN so it picks up the correct network settings. No dramatic reboot of the whole hotel. Just the services and settings that need refreshing.

ipconfig /release
ipconfig /renew
ipconfig /flushdns
ipconfig /all
nslookup www.microsoft.com
ping www.microsoft.com

The new lease shows 10.24.0.10 as the DNS server. The lookup returns an address. The hostname ping resolves. Outlook opens. Websites load. The VPN reconnects cleanly.

06Result — prove it works

I don't close the incident just because the browser loads once. I check the things that were failing, confirm the workstation has the corrected lease, test name resolution again and ask the user to verify the applications they need.

The takeaway

This is why I like troubleshooting from the bottom up. A VPN can say connected. A network icon can look fine. The cable can be seated and the switch port can be green. None of that guarantees that the services people actually depend on are working.

Test the layers. Follow the evidence. Fix the source, not just the symptom. Then test again.

Internet restored. Hotel back online. Berlin Brandenburg Airport can carry on.

After-hours practice · Your turn

Four commands. Four different problems.

Watch each tiny terminal demo first. Then take the keyboard. Each scenario is different: a bad IP configuration, a broken path, a DNS failure or a VPN that never came up. The point is to remember which command helps you ask the next useful question.

01 · Configuration

ipconfig

The workstation says it is connected, but it has no usable network address. Start by inspecting its configuration.

PS C:\IT> Ready when you are.
Your turn

Which command shows the IP address, subnet mask, default gateway and DNS servers?

Tip: the command starts with ipconfig. Add the switch that displays the full configuration.

02 · Reachability

ping

The computer has an address, but users cannot reach anything. Test the gateway first, then an external IP address.

PS C:\IT> Ready when you are.
Your turn

What command tests whether 10.24.18.1 is responding?

Tip: send a small ICMP echo request to the gateway. Then try 1.1.1.1 to test external IP reachability.

03 · VPN route

tracert

The VPN client says connected, but an internal application is unreachable. Trace the route to see whether traffic is entering the expected VPN path.

PS C:\IT> Ready when you are.
Your turn

Which Windows command traces the route to the internal app at 10.80.4.20?

Tip: it is short for trace route. On Windows, use tracert 10.80.4.20 and compare the hops with the expected VPN path.

04 · Name resolution

nslookup

You can ping an external IP, but www.microsoft.com will not load. The connection may be fine; DNS may not be.

PS C:\IT> Ready when you are.
Your turn

Which command asks DNS to resolve www.microsoft.com?

Tip: the command combines “name” and “lookup”. Try nslookup www.microsoft.com.

TRAINING NOTE · These are illustrative outputs, not live network tests. Asterisks in a trace can mean a router does not reply to probes; they do not automatically prove the route is broken.
